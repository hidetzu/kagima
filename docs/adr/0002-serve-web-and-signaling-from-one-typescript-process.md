# 0002. Web と Signaling は 1 つの TypeScript プロセスが提供する

- 状態: **決定**
- 日付: 2026-09-04

## 決定

⚠ **HTTP(画面と API)と WebSocket(signaling)を、TypeScript で書いた 1 つの Node プロセスが
提供する。**

⚠ **v0.1.0 のあいだ、動くプロセスは 1 つである。**

## 文脈

- ブラウザ側は TypeScript になる。⚠ **signaling のメッセージ型は両側で同じものである。**
  ⚠ **言語を割ると、同じ型を二か所に書くことになる**
  (`CLAUDE.md` § 3 — ⚠ **同じ問いに二つの実装を持たない**)。
- ⚠ **ルーム状態は 1 か所にしか置かない**([`0005`](0005-keep-room-state-in-process-memory-only.md))。
  ⚠ **プロセスを分けると、状態が二か所に出るか、状態を共有する仕組みが要る。**
  ⚠ **v0.1.0 にその理由はない。**
- Linux PC で動くこと、将来 Raspberry Pi 等へ持っていけることが条件である
  ([`../PRODUCT.md`](../PRODUCT.md) § 2)。

## 却下した案

| 案 | ⚠ 却下の理由 |
|---|---|
| **Go の単一バイナリ** | ⚠ **配布は楽になるが、ブラウザ側と言語が割れる。** ⚠ **signaling の型を二重に持つ代償のほうが大きい** |
| **Web と Signaling を別プロセスに分ける** | ⚠ **v0.1.0 の規模で分ける理由がない。** ⚠ **ルーム状態の置き場所が問題になるだけである** |
| **サーバフレームワークを入れる** | ⚠ **1 プロセスが必要とする以上のものを入れない**(`CLAUDE.md` § 3)。⚠ **必要になったら ADR を書いて入れる** |
| **UI フレームワークを入れる** | ⚠ **v0.1.0 の画面は 3 つである。** ⚠ **入れる根拠が測れていない** |
| **Serverless / Edge worker に載せる** | ⚠ **WebSocket を張り続ける前提と噛み合わない。** ⚠ **継続コストの話にもなる(Owner 判断)** |

## ⚠ 越えてはならない境界

```text
第 2 のランタイム、第 2 のビルドシステムを、ADR なしに足さない
ルーム状態を、このプロセスの外に出さない
実行時にネットワークへ出ていく依存を足さない
```

## ⚠ しないと決めた主張

- ⚠ **「スケールする」とは言わない。** ⚠ **1 プロセスで足りる規模しか想定していないし、
  何ルームまで持つかを測っていない。**
- ⚠ **「Raspberry Pi で動く」とも、まだ言わない。**
  ⚠ **1 プロセスで動くように作ってあるだけで、Pi 上では動かしていない**
  ([`../DISCOVERY.md`](../DISCOVERY.md) § 7)。

## 影響

- ⚠ **プロセスが落ちると、動いているルームは全部消える。**
  ⚠ **これは欠陥ではなく [`0005`](0005-keep-room-state-in-process-memory-only.md) の帰結である。**
  ⚠ **ただし利用者に何と表示するかは決まっていない**([`../DISCOVERY.md`](../DISCOVERY.md) § 5)。
- CPU 効率は最良ではない。⚠ **v0.1.0 の負荷でそれが効くかは測っていない。**
