# 0006. `ready-for-ai` は AI 自身が付与し、人間のゲートは merge へ移す

- 状態: **決定**
- 日付: 2026-09-04
- ⚠ **これは kagima 自身の開発の進め方を変える決定であり、プロダクトの決定ではない**

## 決定

⚠ **`issue-ready` が `Ready for AI: YES` を返した Issue には、AI 自身が `ready-for-ai` を付与する。**
⚠ **判定根拠を Issue に投稿したうえで、`.claude/tools/ready-for-ai.mjs` から付与する。**

⚠ **付与から PR 作成までは、人間に訊かずに進める。**

⚠ **人間のゲートは merge に置く。** ⚠ **merge の許可は毎回取る。**

⚠ **1 Issue あたりの人間のゲートは 1 つである。** ⚠ **0 にはしない。**

## ⚠ Owner の指示(2026-09-04)

⚠ **以下は Owner の言葉であり、書き換えない。**

> ready-for-ai の付与もOwner作業にせず、自律化してください。issue-ready が YES と判定した
> Issueについては、判定根拠をIssueへ残したうえでAI自身が ready-for-ai を付与し、依存関係を
> 満たしたものから loop-controller で実行してください。着手直前にもReady判定を再実行して
> ください。ただし、needs-decision、未解決dependency、実行環境の不足、Product / Security /
> Privacy / 継続コストに関するOwner判断が残るIssueには付与しないこと。PR作成までは自走して
> 構いません。mergeとOwner判断事項は従来どおりApproval Gateを残してください。この変更自体も
> AI開発基盤の改善として記録し、Telemetry / Evalで「Ownerによるready-for-ai付与回数」を
> 観測できるようにしてください。

## 文脈

⚠ **`docs/PRODUCT.md` § 7 が、開発の進め方そのものをこのリポジトリの主題の半分だと言っている。**
⚠ **「Owner とのやりとりの回数を増やして解決しない」とも書いてある。**

⚠ **移植元テンプレートでは、`ready-for-ai` は人間だけが貼るものだった。**
⚠ **その設計では、人間が最初のゲート(ラベル付与と計画承認)に立ち、そのひとつの承認が
最後の merge までを覆っていた。**

⚠ **ラベル付与を自律化すると、そのゲートが消える。** ⚠ **何もしなければゲートは 0 個になる。**
⚠ **それはこの決定の意図ではない。**

## ⚠ ゲートは弱くなったのではなく、移動した

```text
before   人間がラベルを貼る -> 人間が計画を承認 -> ... -> merge(最初の承認が覆う)
now      AI がラベルを貼る   -> ...              -> PR  -> ⚠ 人間が merge を承認
```

| | before | now |
|---|---|---|
| ラベル付与 | 人間 | ⚠ **AI(条件つき)** |
| 着手の承認 | 人間 | ⚠ **無し** |
| push / PR | 最初の承認に含む | ⚠ **Loop Controller の中では承認済扱い** |
| **merge** | ⚠ **最初の承認に含んでいた** | ⚠ **毎回取る。ここが唯一のゲート** |
| 人間のゲート数 | 1 | ⚠ **1(変わっていない)** |

⚠ **merge を後ろのゲートにしたのは、そこが「戻せない」点だからである。**
⚠ **`.claude/rules/owner-decisions.md` は「間違えても戻せることは自分で決める。戻せないことだけ訊く」
と言っている。** ⚠ **ラベルを貼ることは戻せる。** ⚠ **merge は戻しにくい。**
⚠ **ゲートを戻せる側から戻せない側へ動かしたのであって、外したのではない。**

## ⚠ 付与してはならない条件

⚠ **一覧の持ち主は [`../../.claude/rules/owner-decisions.md`](../../.claude/rules/owner-decisions.md) § `ready-for-ai` である。**
⚠ **ここには写さない** — ⚠ **二か所に書いた時点でどちらかが古くなる。**

⚠ **ただし、そのうち 3 つがなぜ Owner のものであり続けるかは、ここに書く理由がある。**

⚠ **Product / Security / Privacy / 継続コストは、`docs/PRODUCT.md` § 6 が Owner のものと定めた
項目である。** ⚠ **今回の変更はそこに一切触れていない。**
⚠ **自律化したのは「作業を渡してよいかの判定」であって、「何を作るか」でも「何を約束するか」でも
ない。** ⚠ **この区別が崩れたら、この ADR は破られている。**

## 却下した案

| 案 | ⚠ 却下の理由 |
|---|---|
| **ラベルを廃止し、`issue-ready` の YES だけで走る** | ⚠ **ラベルは外から見える状態である。** ⚠ **消すと、何が渡されたのかが GitHub 上から読めなくなる** |
| **ラベル付与を自律化し、merge も自律化する** | ⚠ **人間のゲートが 0 になる。** ⚠ **Owner の指示にも反する** |
| **`gh issue edit --add-label` で貼る** | ⚠ **記録が残らない。** ⚠ **「Owner が何回貼ったか」が原理的に答えられなくなる**(§ 観測) |
| **AI がラベルを外せるようにする** | ⚠ **付与と削除は対称ではない。** ⚠ **Owner が貼ったものを外すのは Owner を上書きすることである** |
| **判定根拠を Issue に残さずに貼る** | ⚠ **根拠のないラベルは、誤って貼られたものと区別がつかない** |
| **merge の承認を「最初に一度」に戻す** | ⚠ **最初のゲートが無くなった以上、それは 0 個と同じである** |

## ⚠ 越えてはならない境界

```text
issue-ready が YES を返していない Issue にラベルを貼らない
needs-decision の付いた Issue にラベルを貼らない
未解決の dependency がある Issue にラベルを貼らない
検証を走らせられない環境の Issue にラベルを貼らない
Product / Security / Privacy / 継続コストが未決の Issue にラベルを貼らない
ラベルを外さない
承認なしに merge しない
--auto / merge queue / --admin を使わない
```

⚠ **`.claude/tools/ready-for-ai.mjs` は、このうち機械的に判定できるものを実際に拒否する。**
⚠ **拒否は答えであって障害ではない。** ⚠ **検査を外して通し直さないこと。**

## ⚠ しないと決めた主張

- ⚠ **「AI が自律的に開発できるようになった」とは言わない。**
  ⚠ **言えるのは「ラベル付与という 1 手順から人間が抜けた」までである。**
- ⚠ **「Owner の手間が減った」とも、まだ言わない。**
  ⚠ **減ったかどうかは観測の対象であって、この ADR の主張ではない**(§ 観測)。
- ⚠ **ラベルが貼られたことは、その Issue が実装可能であることの保証ではない。**
  ⚠ **入場条件にすぎない。** ⚠ **Loop Controller は着手直前に判定をやり直す。**

## 観測

⚠ **`.claude/tools/label-eval.mjs` が「誰が `ready-for-ai` を貼ったか」を並べる。**

```text
observed    ラベルが貼られた回数            GitHub の timeline から
observed    そのうち AI が記録した回数      .claude/telemetry/labels.jsonl から
⚠ INFERRED  残り = Owner が貼った回数       ⚠ 引き算であって測定ではない
```

- ⚠ **`gh` は Owner のアカウントとして動くので、timeline の actor では両者を分けられない。**
  ⚠ **actor を使えば、推測を測定の顔で出すことになる**
  ([`../../.claude/rules/evidence.md`](../../.claude/rules/evidence.md))。
- ⚠ **だから AI 側が自分の付与を記録し、その差分を Owner のものと **推定** する。**
  ⚠ **推定であることは出力に毎回書かれる。** ⚠ **読みやすくするために外さないこと。**
- ⚠ **記録漏れは Owner 側に寄る方向へ偏る。** ⚠ **この問いにとっては安全な向きだが、
  ⚠ 偏っていると言うことと、補正することは別である。** ⚠ **補正はしない。**
- ⚠ **この数字は採点ではない。** ⚠ **Owner の付与回数が 0 だから良い、とは言わない。**

## 影響

- ⚠ **`.claude/` はテンプレートの写しではなくなった。**
  ⚠ **`rules/owner-decisions.md`、`rules/git.md`、`skills/issue-ready`、`skills/loop-controller`
  の 4 つが上流と乖離した。**
- ⚠ **これは上流へ送り返す候補である**(テンプレート README § 5 —
  ⚠ **プロジェクトがテンプレートと戦う羽目になったら、テンプレートのほうが間違っている**)。
  ⚠ **ただし送り返すのは、この形が実際に回ってからである。**
  ⚠ **一般的に聞こえることではなく、動いたことが根拠になる。**
- ⚠ **`README.md` の「移植したもの」表は、もう「原文のまま」ではない。**
  ⚠ **表を更新してある。** ⚠ **古い表を残すほうが、乖離そのものより害が大きい。**
